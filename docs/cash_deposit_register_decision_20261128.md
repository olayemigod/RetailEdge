# Cash Deposit Register — engineering decision and acceptance

## Basis

- Authoritative RetailEdge version-16 base: ce11879ebf7374c2a7d69dc91a8ead23a391eb51. Restored-site QA uses Frappe/ERPNext v16 series; exact current app pins must be recorded before combined acceptance.
- ERPNext Payment Entry (Internal Transfer) is the accounting document. Drafts do not post to GL; submitted entries do. See https://docs.frappe.io/erpnext/payment-entry and https://docs.frappe.io/erpnext/banking-in-erpnext.
- Frappe v16 permission-aware get_list and structured aggregate fields: https://docs.frappe.io/framework/user/en/api/database. Do not use unrestricted get_all or a second deposit ledger.
- Shopify POS register-session activity/history and separate staff permissions are useful operational precedents: https://help.shopify.com/en/manual/sell-in-person/shopify-pos/cash-register-management/register-sessions-in-shopify-pos and https://help.shopify.com/en/manual/sell-in-person/shopify-pos/cash-register-management/cash-tracking-reports-by-location. Do not copy a separate drawer ledger or loosen ERPNext authority.
- Existing RetailEdge Payment History provides branch scoping, pagination, status/period filters and native document read checks. Its Page is accounting-role-only; do not widen access to general payment history just to expose deposits.
- Existing Standard Internal Transfer Completion handles review, workflow and submit. Reuse it in the UI rather than posting directly. PR #259 corrects Select-only account handling; PR #260 separates expense reservations from physical till cash. Both remain independent of the register read service.

## First slice

The read-only GET service lists only marked Cash Deposit/Internal Transfer Payment Entries. It intersects native Payment Entry read permission, Company read permission and operational Branch scope. Cashier-only users are scoped to their own cashier attribution; reviewers with appropriate native permissions may view their permitted Branch population. No permission grant, schema change, posting or closing change. Optional filters never widen authority. Totals use the same permission-aware filtered set as the page, grouped by document state and currency; drafts and cancelled records are not posted deposits. No global counts are returned outside that set.

## Isolated acceptance correction — 2026-11-28

The combined QA candidate passed My Work cash presentation, backup and build, but the role-exact cashier could not see or open the register. Company Read and Page access were true; all generic Payment Entry permissions were false. This matches the deliberate canonical cashier baseline in `test_persona_effective_permissions.py` and the prior customer-receipt engineering decision. Do not change that baseline.

A bounded own-deposit **read-only operational projection** is now available to the canonical cashier without generic Payment Entry Read. This is a documented narrow exception to native Payment Entry list authorization, not a permission grant: require the cashier role, native Company read, operational Branch validation, native POS Opening Shift visibility with matching Company and cashier, fixed deposit/Internal Transfer markers, and the signed-in cashier attribution. Missing or empty scope returns no rows or denies; no arbitrary field selection or unrestricted search. Only business deposit fields are projected; omit ledger-account links and internal timestamps. Rows, aggregate totals and selector choices use the same scope. Authorized native readers still use native permission-aware queries; non-cashier reviewers without native Payment Entry read are denied. Navigation and API access use the same role/authority test. Native draft review and Advanced actions are not exposed in the operational-only projection. No change to posting, draft creation, editing, cancellation, accounting or role grants.

The earlier submitted deposit proves accounting integrity, not that the role-exact cashier could create or submit it. The current generic create path still requires native Payment Entry Create. A separate, source-bound deposit mutation workflow requires deliberate authorization design, workflow checks, reviewed-state/duplicate protection and its own permission acceptance. Do not simulate this with Accounts User or an unrestricted grant.

Regression coverage: reproduce missing native Read with the canonical cashier, verify mandatory own-shift/branch filters and complete status totals, deny other cashier and unverified shift queries, fail closed on unscoped reader use, verify navigation and add actual role-exact browser shortcut → register API coverage. Full exact-head validation and isolated nonempty fixture retest remain pending. The browser fixture is not evidence of the four Neotex records or real submission authority.
